The simulator's timing model **under-predicted p95 TTFT by 5–222×** at this load. Where it predicted no preemptions, the engines had 15, 0, 67, 71, 28, 18, 0, 67, 83, 48. ## Why — post hoc, a lead and not a finding

From vLLM's own 10-second stats lines, in the 27 windows where an engine decoded without any prefill: one decode step ≈ running requests ÷ generation throughput. Coarse, so medians by batch size:

| running requests | windows | median step | the profile predicts |
|---|---:|---:|---:|
| 1–29 (median 19) | 11 | 239 ms | 76 ms |
| 30–59 (median 38) | 8 | 270 ms | 100 ms |
| 60–99 (median 71) | 3 | 566 ms | 140 ms |
| 100+ (median 106) | 5 | 640 ms | 184 ms |

Decode steps took **2.7–4.0 times** what the profile predicts, at every batch size. At two requests per second per engine, each with 64 output tokens, that is enough to tip an engine into overload — the queue grows, the cache fills, requests are preempted and recomputed — which is how a few-times-slower step becomes a 5–222× longer wait. Two candidate causes, neither tested: (1) **context length** — these prompts are ~1,700 tokens, and the per-request decode cost rises with context across three measurements (about 0.2 ms per request at ~100 tokens in C1, about 2 ms at 448 in Phase 3's sweep), while the profile has no context term; (2) **CPU** — two engines and a client streaming ~200 responses shared 4 vCPUs. A single-engine decode sweep across context lengths separates the two.
