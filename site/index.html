kv-routing-sim

Which KV-cache routing policy should you run — and on how many GPUs? A simulator whose cache model was checked against a live vLLM, and whose tests were written down before they ran.

Run it on your own traffic

Keep each user on one GPU. On three calibrations of the same T4, session-sticky routing needs the fewest GPUs — or ties for them — at every load with one shared system prompt and with four, and never needs more than round-robin or least-loaded. Whether routing by prefix then saves GPUs with 64 tenants' prompts is not settled: the registered test said no on one calibration and yes on two others. Read every GPU count as ± one.

This is not a new result. SMetric (Wang et al., arXiv 2607.08565, July 2026) reached the same advice from production traces on 32 real GPUs, and LMetric (Zhang et al., OSDI '26) showed why a hand-set weight between cache and load has no right value. What is here is an independent agreement on a small calibrated model, from tests registered before they ran. Both published policies were then ported and run here on a public production trace: under a first-token target neither needed more GPUs than session-sticky, and neither clearly fewer. SMetric also names a weakness these grids cannot show: real sessions differ widely in size, and plain session-sticky routing then leaves the load unbalanced. Every generated session here has the same number of turns. NVIDIA's Dynamo ships a larger simulator for the same question (AISimulate). The prior-art file in the repository says what an earlier check missed.

Scope, before you trust it. Generated agentic traffic, Qwen3-4B, and T4 timings from a context-aware model that predicted held-out traffic within 1.41× and two live T4s within 1.02–1.79×. The target on this page is on the first token only. With a limit on the time per token as well (100 ms), which kvsim replay applies by default, the simulator needs about twice as many GPUs; its per-token model was checked on a live T4 within 7% on three workloads around that limit, on one replica. This finding changed twice. On the first, context-free timing model, which was 5–222× optimistic on live GPUs, prefix routing won once prompts outgrew one GPU's cache. Re-tested on the validated model (calibration A), that half was falsified; on two more calibrations of the same T4 (B and C, measured with kvsim calibrate on a live engine), it held. The three calibrations agree on a GPU count to within one at 96% of points, and that half of the finding was decided by one. The explorer below shows calibration A. On Mooncake's real traces, re-run on the validated model on two calibrations, session-sticky and prefix-affinity are within one replica of each other at every speed.

Run it on your own traffic

Open the simulator in your browser to size a fleet for generated traffic or your own serving log, on the measured T4 or on your GPU's profile. The file you choose is read on your computer and never uploaded.

Or install the command line:

pip install git+https://github.com/gitgod-debug/kv-routing-sim
kvsim replay your-trace.jsonl --policies all --replicas 1-16 \
  --profile t4-qwen3-4b-vllm0.30.0-ctx --cost-model default
Every number on this page comes from committed scripts with pinned seeds, in the repository.
