kv-routing-sim

Which KV-cache routing policy should you run, and on how many GPUs? This simulator answers that. Its cache model was checked against a live vLLM, and its tests were written down before they ran.

Run it on your own traffic Explore the results

Keep each user on one GPU. This holds on three calibrations of the same GPU type (a T4). Session-sticky routing needs the fewest GPUs, or ties for the fewest, at every load, with one shared system prompt and with four. It never needs more GPUs than round-robin or least-loaded. With 64 tenants' prompts, it is not settled whether routing by prefix saves GPUs. The registered test said no on one calibration and yes on two others. Another calibration usually gives a count within one GPU of each count shown here.

This is not a new result. SMetric (Wang et al., arXiv 2607.08565, July 2026) reached the same advice from production traces on 32 real GPUs. LMetric (Zhang et al., OSDI '26) showed why a hand-set weight between cache and load has no right value. What is here is an independent agreement on a small calibrated model, from tests registered before they ran. Both published policies were then ported and run here on a public production trace. Under a first-token target, neither needed more GPUs than session-sticky. SMetric's rule needed one fewer at the highest load on all four calibrations, and LMetric on one. SMetric also names a weakness that these grids cannot show. Real sessions differ a lot in size, and plain session-sticky routing then leaves the load unbalanced. Every generated session here has the same number of turns. NVIDIA's Dynamo ships a larger simulator for the same question (AISim). Three more simulators checked against live engines were published in October and November 2026. The related-work section of the README names them and says what earlier checks missed.

Scope, before you trust it. Generated agent traffic, Qwen3-4B, and T4 timings from a context-aware model. That model predicted held-out traffic within 1.41×, and two live T4s within 1.02–1.79×. The target on this page is on the first token only. With a limit on the time per token as well (100 ms), which kvsim replay applies by default, the simulator needs about twice as many GPUs. Its per-token model was checked on a live T4: within 7% on three workloads around that limit, on one replica. This finding changed twice. On the first timing model, which had no context term and was 5–222× optimistic on live GPUs, prefix routing won once prompts outgrew one GPU's cache. Tested again on the validated model (calibration A), that half was falsified. On two more calibrations of the same GPU type (B and C, measured with kvsim calibrate on a live engine), it held. Where all three calibrations give a GPU count (92 of 144 points), they agree within one at 89, and that half of the finding was decided by one GPU. At 8 more points they disagree on whether the target can be held at all. The explorer below shows calibration A. On Mooncake's real traces, run again on the validated model on two calibrations, session-sticky and prefix-affinity are within one replica of each other at every speed.

Run it on your own traffic

Open the simulator in your browser to size a fleet for generated traffic or your own serving log, on the measured T4 or on your GPU's profile. The file you choose is read on your computer and never uploaded.

Or install the command line:

pip install kv-routing-sim
kvsim replay your-trace.jsonl --policies all --replicas 1-16 \
  --profile t4-qwen3-4b-vllm0.30.0-ctx --cost-model default
Every number on this page comes from committed scripts with pinned seeds, in the repository. How it was measured, and every registered test: the README.
