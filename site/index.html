kv-routing-sim

Which KV-cache routing policy should you run — and on how many GPUs? A simulator whose cache model was checked against a live vLLM, and whose tests were written down before they ran.

Keep each user on one GPU. On three calibrations of the same T4, session-sticky routing needs the fewest GPUs — or ties for them — at every load with one shared system prompt and with four, and never needs more than round-robin or least-loaded. Whether routing by prefix then saves GPUs with 64 tenants' prompts is not settled: the registered test said no on one calibration and yes on two others. Read every GPU count as ± one.

Scope, before you trust it. Generated agentic traffic, Qwen3-4B, T4 timings from a context-aware model that predicted held-out traffic within 1.41× and, after the fact, two live T4s within 1.02–1.79× (C2). The target is on the first token only; time per token is not yet part of it. This finding changed twice. On the first, context-free timing model — 5–222× optimistic on live GPUs — prefix routing won once prompts outgrew one GPU's cache. Re-tested on the validated model (2026-09-30, calibration A), that half was falsified. On 2026-10-05 the same test was run on two more calibrations of the same T4 (B and C, written by kvsim calibrate on a live engine): it held on both. The three calibrations agree on a GPU count to within one at 96% of points, and that half of the finding was decided by one. The explorer below shows calibration A. On real traces (run on the first model) session-sticky and prefix-affinity came out within one replica of each other.
